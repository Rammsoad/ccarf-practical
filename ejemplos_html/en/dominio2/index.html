Demo 2.1 · Tool descriptions and selection

What is this demo about? (click to hide)

📖 What this demo is about

Claude picks a tool by reading only three things: its name, its description and its input_schema. It doesn't see your code or know what the function does inside. If two descriptions look alike, the selection becomes a coin toss. Improving the descriptions is the first fix, before few-shot examples or a classifier.

🧪 What to expect

  • The names already say a lot, so with the minimal ones Claude will get several right. The differences show up in the edge cases:
  • "How much was I charged for shipping on order #12347?" → with minimal descriptions it tends to go to get_shipping_rates because of the word "shipping". The right one is lookup_order, because it's an order already placed.
  • "My order hasn't arrived, my email is…" → with minimal descriptions it tends to go to lookup_order because of the word "order". The right one is get_customer, because there's no order number and the email gets you the list.
  • Also look at the input: with query Claude sends the whole sentence; with email, order_id or codigo_postal it sends just the piece of data.
  • Results can vary between runs. That itself is part of the lesson.

🎓 What the exam asks

  • Minimal or overlapping description → unreliable selection. Fix: descriptions with input format, examples, edge cases and boundaries.
  • Rename tools to remove overlaps, or split a generic tool into several with a clear purpose.
  • Check the system prompt when a tool gets picked "for no reason".

How to read each card: at the top, the variables of that run (in yellow, what changed compared to the previous one). Then the diagram, with its color legend. At the end, in green, 👉 the conclusion: what you should take away.

Demo 2.2 · Structured vs generic errors

What is this demo about? (click to hide)

📖 What this demo is about

What your tool returns to Claude when something goes wrong. There are two classic mistakes:

  1. Generic error ("Operation failed"): Claude doesn't know whether to retry, ask for other data or escalate.
  2. Silenced error: the system failed, but the tool returns an empty list. Claude thinks the query worked and tells the customer something false ("you have no orders").

The solution is a structured error: is_error: true and in the content errorCategory (transient, validation, business or permission), isRetryable and a readable description. And an empty result that is valid is not an error.

🧪 What to expect

  • caido · generico is the key moment: Claude says there are no orders, when in fact the system was down. In structured it retries and gets the orders on the 2nd attempt.
  • With the generic one, Claude sometimes guesses right (for example, it notices ana@ejemplo is misspelled), but it does it on its own: the tool didn't give it that information.
  • The final table puts the calls, the answer and what should happen side by side.

🎓 What the exam asks

  • Structured error metadata so the agent can decide: retry, explain or escalate.
  • Distinguish an access failure from a valid empty result.
  • In multi-agent setups: the subagent retries what's transient locally and propagates to the coordinator only what it couldn't resolve, with what it tried and partial results. Don't suppress errors or stop everything because of a single failure.

How to read each card: at the top, the variables of that run (in yellow, what changed compared to the previous one). Then the diagram, with its color legend. At the end, in green, 👉 the conclusion: what you should take away.

Demo 2.3 · Too many tools and tool_choice

What is this demo about? (click to hide)

📖 What this demo is about

Two design decisions: how many tools to give each agent (part A) and how to force it to use one (part B, tool_choice).

🧪 What changes from one run to another

  • D23_TOOLS_A = "18" (or "4"): runs part A with only that configuration.

🎓 What the exam asks

  • 18 tools instead of 4 or 5 → worse selection. Each subagent gets only the tools for its role.
  • Replace generic tools with restricted versions; give a narrow shared tool (e.g. verify_fact) when a role needs it often.
  • tool_choice: any guarantees a call; forcing a tool guarantees the order (e.g. extract metadata first).

What is this demo about? (click to hide)

📖 What this demo is about

MCP (Model Context Protocol): a standard for an agent to discover and use tools and data from external systems. An MCP server offers:

  • Tools: actions Claude can call.
  • Resources: data that can be read, like a catalog or documentation.

The demo creates its own server, first talks to it without Claude and then connects it to an agent.

🧪 What changes from one run to another

  • D24_USAR_RESOURCES = True: the agent also gets ListMcpResourcesTool and ReadMcpResourceTool, and can read the full catalog instead of searching blindly.
  • Make the description of buscar_producto worse (for example, "Busca.") and compare.
  • Open servidor_inventario_mcp.py and add a new tool. The lab doesn't overwrite your version if the file already exists; delete it to go back to the original.
  • D24_SECRETO = "en_archivo": the token ends up written in the .mcp.json that goes into git.
  • D24_ALCANCE = "usuario": the server ends up in ~/.claude.json and your teammate doesn't have it.

🎓 What the exam asks

  • The project's .mcp.json vs the user's ~/.claude.json, and ${VAR} variable expansion for secrets.
  • The tools from every configured server are discovered on connecting and become available at once.
  • Improve MCP tool descriptions so the agent doesn't ignore them and use built-ins like Grep instead.
  • Resources as a content catalog to save exploratory calls.
  • Community servers for standard integrations; your own only for the team's specific flows.

Demo 2.5 · Built-in tools: Grep, Glob, Read, Edit (Agent SDK)

What is this demo about? (click to hide)

📖 What this demo is about

Claude Code's built-in tools and when to use each one:

| Tool | What for | |---|---| | Grep | Search for content inside files (who calls a function, an error message) | | Glob | Search for files by name or path pattern (**/*.test.ts); it doesn't look at content | | Read | Read a file | | Edit | Targeted change: replaces text that must be unique; if it isn't, it fails | | Write | Overwrite the whole file (fallback when Edit can't) |

🧪 What changes from one run to another

  • Remove "Grep" from D25_TOOLS: it will have to open file by file with Read (more turns and tokens).
  • D25_EDIT_RESPALDO = "read_write" (with "Write" in D25_TOOLS): the Edit of just 10000 fails because the text repeats and the agent uses Read + Write, which is what the exam expects.
  • Remove "Glob": finding the *.test.ts files gets harder.
  • Change D25_TAREA to ask it to change "the 10000" without saying which, and watch the Edit error.

🎓 What the exam asks

  • Grep for content, Glob for paths, Edit for targeted changes with unique text, and Read + Write as the fallback.
  • Explore incrementally: Grep to find entry points and Read to follow imports, instead of reading everything.
  • Trace a function across modules that re-export it: identify the exported names and search for each one.
