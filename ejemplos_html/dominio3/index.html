Demo 3.1 · Jerarquía de CLAUDE.md (Agent SDK)

¿De qué va esta demo? (clic para ocultar)

📖 De qué trata esta demo

Claude Code junta instrucciones de varios archivos CLAUDE.md y cada uno tiene un alcance distinto. La pregunta del examen siempre es la misma: ¿dónde vive esta instrucción y quién la recibe?

| Archivo | Alcance | ¿Va a git? | |---|---|---| | ~/.claude/CLAUDE.md | Solo tú, en todos tus proyectos | No | | CLAUDE.md (raíz del repo) | Todo el equipo | Sí | | CLAUDE.local.md | Solo tú, en este repo | No (.gitignore) | | src/api/CLAUDE.md (subcarpeta) | Quien trabaje en esa carpeta | Sí | | @docs/estilo.md dentro de un CLAUDE.md | Importa otro archivo | Según dónde esté |

La demo no toca tu ~/.claude/CLAUDE.md. El caso "personal" se muestra con CLAUDE.local.md.

🧪 Qué cambia entre una corrida y otra

  • D31_USAR_IMPORT = False: docs/estilo.md ya no se carga y el agente deja de conocer la regla de montos.
  • D31_SIMULAR_COMPANERO = True: corre como alguien nuevo del equipo (setting_sources=["project"]). CLAUDE.local.md desaparece. Es el caso clásico del examen: la regla del equipo estaba en un archivo personal. El arreglo es moverla al CLAUDE.md del repo.
  • Pide leer src/carrito/total.ts en vez de reembolsos.ts: src/api/CLAUDE.md no se carga.

🎓 Lo que pregunta el examen

  • Un compañero nuevo no recibe una instrucción → estaba en ~/.claude/CLAUDE.md (personal). Va en el CLAUDE.md del repo.
  • Importar con @ruta (no existe @import) para mantener CLAUDE.md modular; .claude/rules/ para separar por tema.
  • /memory para ver qué archivos de memoria están cargados y diagnosticar comportamientos inconsistentes.

Demo 3.2 · Slash commands y skills (Agent SDK)

¿De qué va esta demo? (clic para ocultar)

📖 De qué trata esta demo

Dos formas de empaquetar un flujo para reutilizarlo:

| | Slash command | Skill | |---|---|---| | Quién lo dispara | Tú: /revisar-reembolso #12346 | Claude, cuando la tarea coincide con la descripción | | Dónde vive | .claude/commands/<nombre>.md | .claude/skills/<nombre>/SKILL.md | | Personal | ~/.claude/commands/ | ~/.claude/skills/ | | Contexto | Se manda completo al invocarlo | Al inicio solo nombre + descripción; el cuerpo se carga al usarlo |

Regla para decidir: lo que siempre aplica va en CLAUDE.md; lo que tú invocas, en un command; lo que Claude debe decidir usar, en un skill.

🧪 Qué cambia entre una corrida y otra

  • D32_DESCRIPCION_SKILL = "vaga" ("Utilidades varias."): es probable que Claude no use el skill. Es la misma lección de la demo 2.1: la descripción decide.
  • D32_PEDIDO = "#12345": $1,850 con foto → debería salir CUMPLE.
  • Abre la carpeta del proyecto (la ruta sale en pantalla) y crea tu propio comando.

🎓 Lo que pregunta el examen

  • Comando del equipo → .claude/commands/ (va a git). Personal → ~/.claude/commands/.
  • Frontmatter de skills: context: fork corre el skill en un subagente aislado; allowed-tools limita qué tools usa; argument-hint indica qué argumento espera.
  • Skill = a demanda; CLAUDE.md = siempre cargado.

Demo 3.3 · Reglas por ruta en .claude/rules (Agent SDK)

¿De qué va esta demo? (clic para ocultar)

📖 De qué trata esta demo

Las reglas por ruta son archivos en .claude/rules/ con un frontmatter paths: que contiene globs. Claude Code carga cada regla solo cuando trabaja con archivos que coinciden. Así las convenciones de pruebas no ocupan contexto cuando editas la API, y al revés.

¿Por qué no un CLAUDE.md en una subcarpeta? Porque los tests están regados por todo el repo. Un glob **/*.test.ts los alcanza a todos; un CLAUDE.md solo cubre su carpeta.

🧪 Qué cambia entre una corrida y otra

  • D33_CON_PATHS = False: las dos reglas aparecen al iniciar la sesión, aunque no toques esos archivos. Funciona, pero gasta contexto en todo momento.
  • Cambia D33_PREGUNTA para leer solo src/carrito/total.ts: no se carga ninguna regla.

🎓 Lo que pregunta el examen

  • Convenciones para un tipo de archivo regado por el repo → .claude/rules/ con paths (glob), no un CLAUDE.md por carpeta.
  • Ventaja: se cargan solo cuando aplican, así que reducen tokens y ruido.

Demo 3.4 · Plan mode vs ejecución directa (Agent SDK)

¿De qué va esta demo? (clic para ocultar)

📖 De qué trata esta demo

Plan mode (permission_mode="plan"): Claude explora y propone un plan, pero no puede editar archivos. Úsalo cuando la tarea es grande o ambigua: conviene ver el plan antes de que se edite nada. Plan mode es para cambios grandes (una migración de 45 archivos), con varias formas válidas o con decisiones de arquitectura. Un cambio claro y acotado (cambiar un valor en 3 archivos) va con ejecución directa. El patrón híbrido combina ambas: planear → revisar/aprobar → ejecutar.

🧪 Qué cambia entre una corrida y otra

  • Corre los 3 valores de D34_MODO y compara la tabla final.
  • Lee el plan de la fase 1: ¿encontró los 3 lugares? Si no, el valor del plan es que tú lo notas antes de que se edite nada.
  • D34_TIPO_TAREA = "clara" o "ambigua": plan mode conviene si hay varias formas válidas o el cambio es grande; un cambio claro y acotado va directo.

🎓 Lo que pregunta el examen

  • Migraciones, cambios de arquitectura o tareas con varias soluciones posibles → plan mode.
  • Bug con causa clara en un solo archivo → ejecución directa.
  • Explorar con un subagente para no llenar el contexto principal; planear antes de ejecutar.

Demo 3.5 · Refinamiento iterativo: ejemplos y TDD

¿De qué va esta demo? (clic para ocultar)

📖 De qué trata esta demo

Cómo corregir un resultado que no sale como quieres. Las técnicas del examen:

  • Ejemplos concretos de entrada → salida, en lugar de describir con adjetivos.
  • TDD: primero las pruebas; luego pides el código y le compartes las pruebas que fallaron.
  • Interview pattern: en tareas poco claras, que Claude te haga preguntas antes de implementar.
  • Arreglos relacionados en un solo mensaje; independientes, uno por uno.

🧪 Qué cambia entre una corrida y otra

  • Corre los 3 modos y compara. Lo usual: "vago" falla en los casos frontera, "ejemplos" acierta más desde la primera ronda y "tdd" converge en 2 o 3 rondas.
  • Agrega un caso nuevo a CASOS_35 (por ejemplo, con extensión ext. 12) y mira cómo lo resuelve TDD.

🎓 Lo que pregunta el examen

  • Las descripciones en prosa se interpretan de forma inconsistente → da 2 o 3 ejemplos concretos.
  • Iterar compartiendo las pruebas que fallan (entrada, obtenido y esperado) converge mejor que "no funciona, arréglalo".

Demo 3.6 · CI/CD con claude -p (Claude Code)

¿De qué va esta demo? (clic para ocultar)

📖 De qué trata esta demo

Claude Code en un pipeline de CI/CD, donde no hay nadie para contestar. Sin -p, Claude Code abre una sesión interactiva y el job se queda colgado esperando.

| Flag | Para qué | |---|---| | -p "prompt" (--print) | Corre, imprime el resultado y termina | | --output-format json | Salida que el pipeline puede leer: result, total_cost_usd, session_id… | | --json-schema '<schema>' | La respuesta se valida contra tu schema y llega en structured_output | | --allowedTools, --tools | Qué puede usar (aquí solo Read) | | --max-turns, --max-budget-usd | Límites de turnos y de gasto |

🧪 Qué cambia entre una corrida y otra

  • D36_FORMATO = "text": la salida es prosa y el pipeline no puede decidir nada con ella.
  • D36_CON_SCHEMA = False: hay JSON, pero result sigue siendo texto libre.
  • Edita cambios.diff en la demo para que respete el límite: debería aprobar.

🎓 Lo que pregunta el examen

  • El job de CI se cuelga → falta -p.
  • Salida para procesar → --output-format json + --json-schema.
  • El revisor debe ser una sesión independiente de la que generó el código: no se autorrevisa.
  • CLAUDE.md da contexto del proyecto también en CI. Incluye hallazgos previos para no repetir comentarios en cada push.
  • claude -p para revisiones bloqueantes antes del merge; Message Batches API (Dominio 4) para trabajos que pueden esperar.
