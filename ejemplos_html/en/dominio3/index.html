Demo 3.1 · CLAUDE.md hierarchy (Agent SDK)

What is this demo about? (click to hide)

📖 What this demo is about

Claude Code gathers instructions from several CLAUDE.md files and each one has a different scope. The exam's question is always the same: where does this instruction live and who receives it?

| File | Scope | Goes into git? | |---|---|---| | ~/.claude/CLAUDE.md | Only you, in all your projects | No | | CLAUDE.md (repo root) | The whole team | Yes | | CLAUDE.local.md | Only you, in this repo | No (.gitignore) | | src/api/CLAUDE.md (subfolder) | Whoever works in that folder | Yes | | @docs/estilo.md inside a CLAUDE.md | Imports another file | Depends on where it is |

The demo doesn't touch your ~/.claude/CLAUDE.md. The "personal" case is shown with CLAUDE.local.md.

🧪 What changes from one run to another

  • D31_USAR_IMPORT = False: docs/estilo.md no longer loads and the agent stops knowing the amounts rule.
  • D31_SIMULAR_COMPANERO = True: runs as someone new on the team (setting_sources=["project"]). CLAUDE.local.md disappears. It's the classic exam case: the team's rule was in a personal file. The fix is to move it to the repo's CLAUDE.md.
  • Ask it to read src/carrito/total.ts instead of reembolsos.ts: src/api/CLAUDE.md doesn't load.

🎓 What the exam asks

  • A new teammate doesn't get an instruction → it was in ~/.claude/CLAUDE.md (personal). It goes in the repo's CLAUDE.md.
  • Import with @path (there is no @import) to keep CLAUDE.md modular; .claude/rules/ to split by topic.
  • /memory to see which memory files are loaded and diagnose inconsistent behavior.

Demo 3.2 · Slash commands and skills (Agent SDK)

What is this demo about? (click to hide)

📖 What this demo is about

Two ways to package a flow for reuse:

| | Slash command | Skill | |---|---|---| | Who triggers it | You: /revisar-reembolso #12346 | Claude, when the task matches the description | | Where it lives | .claude/commands/<name>.md | .claude/skills/<name>/SKILL.md | | Personal | ~/.claude/commands/ | ~/.claude/skills/ | | Context | Sent in full when invoked | At first only name + description; the body loads when used |

Rule for deciding: what always applies goes in CLAUDE.md; what you invoke, in a command; what Claude should decide to use, in a skill.

🧪 What changes from one run to another

  • D32_DESCRIPCION_SKILL = "vaga" ("Utilidades varias.", miscellaneous utilities): Claude will probably not use the skill. It's the same lesson as demo 2.1: the description decides.
  • D32_PEDIDO = "#12345": $1,850 with a photo → it should come out CUMPLE (complies).
  • Open the project folder (the path is shown on screen) and create your own command.

🎓 What the exam asks

  • A team command → .claude/commands/ (goes into git). Personal → ~/.claude/commands/.
  • Skill frontmatter: context: fork runs the skill in an isolated subagent; allowed-tools limits which tools it uses; argument-hint says which argument it expects.
  • Skill = on demand; CLAUDE.md = always loaded.

Demo 3.3 · Path rules in .claude/rules (Agent SDK)

What is this demo about? (click to hide)

📖 What this demo is about

Path rules are files in .claude/rules/ with a paths: frontmatter containing globs. Claude Code loads each rule only when it works with matching files. That way the test conventions don't take up context when you edit the API, and vice versa.

Why not a CLAUDE.md in a subfolder? Because the tests are scattered all over the repo. A **/*.test.ts glob reaches all of them; a CLAUDE.md only covers its own folder.

🧪 What changes from one run to another

  • D33_CON_PATHS = False: both rules appear at session start, even if you don't touch those files. It works, but it spends context all the time.
  • Change D33_PREGUNTA to read only src/carrito/total.ts: no rule loads.

🎓 What the exam asks

  • Conventions for a file type scattered across the repo → .claude/rules/ with paths (glob), not a CLAUDE.md per folder.
  • Advantage: they load only when they apply, so they reduce tokens and noise.

Demo 3.4 · Plan mode vs direct execution (Agent SDK)

What is this demo about? (click to hide)

📖 What this demo is about

Plan mode (permission_mode="plan"): Claude explores and proposes a plan, but can't edit files. Use it when the task is large or ambiguous: it's worth seeing the plan before anything gets edited. Plan mode is for large changes (a 45-file migration), with several valid approaches or with architectural decisions. A clear, well-scoped change (changing a value in 3 files) goes with direct execution. The hybrid pattern combines both: plan → review/approve → execute.

🧪 What changes from one run to another

  • Run the 3 values of D34_MODO and compare the final table.
  • Read the phase 1 plan: did it find the 3 places? If not, the plan's value is that you notice before anything gets edited.
  • D34_TIPO_TAREA = "clara" or "ambigua": plan mode is worth it if there are several valid approaches or the change is large; a clear, well-scoped change goes direct.

🎓 What the exam asks

  • Migrations, architectural changes or tasks with several possible solutions → plan mode.
  • A bug with a clear cause in a single file → direct execution.
  • Explore with a subagent so the main context doesn't fill up; plan before executing.

Demo 3.5 · Iterative refinement: examples and TDD

What is this demo about? (click to hide)

📖 What this demo is about

How to correct a result that doesn't come out the way you want. The exam's techniques:

  • Concrete examples of input → output, instead of describing with adjectives.
  • TDD: tests first; then you ask for the code and share the tests that failed with it.
  • Interview pattern: on unclear tasks, have Claude ask you questions before implementing.
  • Related fixes in a single message; independent ones, one at a time.

🧪 What changes from one run to another

  • Run the 3 modes and compare. The usual: "vago" fails on the edge cases, "ejemplos" gets more right from the first round and "tdd" converges in 2 or 3 rounds.
  • Add a new case to CASOS_35 (for example, with an extension ext. 12) and see how TDD handles it.

🎓 What the exam asks

  • Prose descriptions get interpreted inconsistently → give 2 or 3 concrete examples.
  • Iterating by sharing the failing tests (input, got and expected) converges better than "it doesn't work, fix it".

Demo 3.6 · CI/CD with claude -p (Claude Code)

What is this demo about? (click to hide)

📖 What this demo is about

Claude Code in a CI/CD pipeline, where there's nobody to answer. Without -p, Claude Code opens an interactive session and the job hangs waiting.

| Flag | What for | |---|---| | -p "prompt" (--print) | Runs, prints the result and exits | | --output-format json | Output the pipeline can read: result, total_cost_usd, session_id… | | --json-schema '<schema>' | The answer is validated against your schema and arrives in structured_output | | --allowedTools, --tools | What it can use (here only Read) | | --max-turns, --max-budget-usd | Turn and spending limits |

🧪 What changes from one run to another

  • D36_FORMATO = "text": the output is prose and the pipeline can't decide anything with it.
  • D36_CON_SCHEMA = False: there's JSON, but result is still free text.
  • Edit cambios.diff in the demo so it respects the limit: it should approve.

🎓 What the exam asks

  • The CI job hangs → -p is missing.
  • Output to be processed → --output-format json + --json-schema.
  • The reviewer must be a session independent from the one that generated the code: it doesn't review itself.
  • CLAUDE.md gives project context in CI too. Include previous findings so it doesn't repeat comments on every push.
  • claude -p for blocking reviews before the merge; Message Batches API (Domain 4) for jobs that can wait.
